# Проектирование и нормализация базы данных

Лабораторная работа № 4, вариант 69. Исполнитель — Баринов Кирилл Вадимович. Цель — спроектировать учебную реляционную модель для возможного локального архива QR-кодов.

## Границы модели

По ТЗ работающий прототип создаёт QR-код в браузере, не требует регистрации и не отправляет введённую строку на сервер. Сохранение истории, профилей и меток — **гипотетическое расширение**, используемое для моделирования; оно не реализовано в приложении. База не подключена к генератору. Если хранение когда-нибудь будет реализовано, включать его необходимо только осознанно и локально; сохранённый текст может содержать чувствительные данные.

В модели запись содержит исходную строку, тип ввода, дату и ссылку на параметры вывода. Один профиль можно применить к нескольким записям. Для примера отношения многие-ко-многим добавлены необязательные метки: запись может иметь несколько меток, и метка может принадлежать нескольким записям. Бинарное изображение не хранится: QR можно повторно сформировать из исходных данных и параметров. Модель не описывает учётные записи или серверную синхронизацию.

## Исходная структура

Условная ненормализованная запись `QR_Flat(entry_id, content, input_kind, profile_id, profile_name, error_correction, image_size, [label_id, label_name]...)` объединяет данные записи, профиля и повторяющуюся группу меток. Повторение параметров профиля создаёт избыточность: изменение его названия требует менять много строк. Удаление последней записи может стереть сведения о профиле; создание метки без записи затруднено.

## 1NF

Повторяющуюся группу меток раскладываем на отдельные строки с атомарными атрибутами. Промежуточное отношение `EntryLabelFlat(entry_id, label_id, content, input_kind, profile_id, profile_name, label_name, ...)` имеет составной ключ `(entry_id, label_id)`. Записи без меток и отдельно определённые профили должны представляться самостоятельными строками, без фиктивных значений.

## 2NF

В промежуточном отношении `entry_id → content, input_kind, profile_id`, а `label_id → label_name`: эти атрибуты зависят от части составного ключа. Выделяем `qr_entries` и `labels`, а в `entry_labels` оставляем только пару внешних ключей. Оба поля пары необходимы для идентификации связи; у промежуточной таблицы нет неключевых атрибутов.

## 3NF

Если бы имя профиля и его настройки сохранялись в `qr_entries`, возникала бы транзитивная зависимость `entry_id → profile_id → profile_name, error_correction, image_format, image_size_px, quiet_zone_modules`. Выносим настройки в `qr_profiles`, в записи оставляем внешний ключ. В каждой итоговой таблице неключевые атрибуты зависят от ключа своей сущности. Уникальные имена меток и профилей являются альтернативными ключами.

## Итоговая схема и связи

- `qr_profiles`: первичный ключ `profile_id`, уникальное название и параметры вывода; один профиль — много QR-записей. Удаление используемого профиля запрещено.
- `qr_entries`: первичный ключ `entry_id`, тип `url`/`text`, строка, профиль и время создания. Размер строки ограничен 1000 байтами UTF-8 при UTF-8 кодировке базы.
- `labels`: первичный ключ `label_id` и уникальное имя метки без различия регистра ASCII.
- `entry_labels`: составной ключ `(entry_id, label_id)` и два внешних ключа; реализует M:N. Удаление записи или метки каскадно удаляет соответствующие связи.

Индексы ускоряют поиск записей по профилю и времени и поиск связей по метке. Индекс по `entry_id` обеспечивается составным первичным ключом. В SQLite внешние ключи необходимо включать для каждого соединения: `PRAGMA foreign_keys=ON`. Проверка `trim` в SQLite не заменяет проверку всех Unicode-пробелов, а SQL-схема не проверяет корректность URL — при использовании модели нужна та же прикладная валидация, что в `validation.js`. Даты приложения следует сохранять в едином UTC-формате. Менять существующий профиль нельзя, если требуется воспроизводить исторические результаты: при изменении параметров следует создавать новый профиль.

## Проверка

В пустой базе: `sqlite3 demo.sqlite < database/schema.sql`, затем `sqlite3 demo.sqlite < database/seed_data.sql`. В новом соединении сначала включить внешние ключи и выполнить `PRAGMA foreign_key_check` и `PRAGMA integrity_check`. Проверены заполнение кириллицей, целостность, уникальность связей и меток, ограничения и каскадное удаление.

Автоматизированная проверка: `python3 -m unittest discover -s tests -p 'test_database.py' -v`. Проверяется регистрационная уникальность имён меток для символов ASCII; стандартный SQLite NOCASE не выполняет полное сравнение регистра кириллицы.
